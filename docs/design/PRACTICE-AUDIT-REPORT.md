## 1. Contract Audit

### 1.1 Endpoint Path and Method

- **[PASS]** iOS sends `POST {GAME_SERVER_URL}/api/practice/start` with `{ "deck_id": "..." }` and `Authorization: Bearer <jwt>`.
  - `MatchmakingService.swift` line 153: URL is `"\(gameServerURL)/api/practice/start"`.
  - `index.ts` line 248: `app.post('/api/practice/start', ...)`.
  - Exact match.

### 1.2 Request Body Format

- **[PASS]** iOS sends `{ "deck_id": "<uuid>" }` via `JSONEncoder`.
  - `PracticeRequest` struct uses `CodingKeys` to map `deckId` to `"deck_id"`.
  - Server destructures `req.body.deck_id` and validates it is a string.
  - UUID is encoded as a string by Swift's `JSONEncoder` (standard behavior for `UUID`).

### 1.3 Success Response Decoding

- **[PASS]** Server responds with `{ "match_id": "...", "bot_name": "..." }` (snake_case JSON).
  - `index.ts` line 351-354: `res.json({ match_id: matchId, bot_name: 'Kael, the Bound Tyrant' })`.
  - `PracticeResponse` struct uses `CodingKeys` to map `matchId` from `"match_id"` and `botName` from `"bot_name"`.
  - Exact match.

### 1.4 Match Channel Subscription

- **[PASS]** iOS uses `match_id` to connect to Supabase Realtime channel `match:<matchId>`, same as PvP.
  - The spec confirms (Section 4.4) that `BattleContainerView` connects identically for PvP and practice.
  - Server calls `setupMatchChannel(matchId)` which subscribes to `match:${matchId}`.
  - No new channel naming convention introduced.

### 1.5 Error Response Handling

- **[PASS]** Server returns `{ "error": "..." }` for all error codes (400, 401, 500).
  - `index.ts` lines 253, 260, 275, 288, 378: all use `res.status(N).json({ error: '...' })`.
  - iOS decodes via `PracticeErrorBody` struct with single `error: String` field.
  - Exact match.

## 2. Security Audit

### 2.1 JWT Validation

- **[PASS]** JWT is verified via `supabase.auth.getUser(token)` -- not just decoded, actually validated against Supabase Auth.
  - `verifySupabaseJWT()` in `index.ts` lines 228-240 extracts the token from the `Bearer` prefix, calls `supabase.auth.getUser(token)`, and returns `data.user.id` only on success.
  - Uses the service role client (initialized with `SUPABASE_SERVICE_ROLE_KEY`), which has permission to validate any user token.

### 2.2 Deck Ownership Check

- **[PASS]** Player can only use their own deck. Deck query filters by `owner_id`.
  - `index.ts` line 283: `.eq('owner_id', player.id)` ensures the deck belongs to the authenticated player.
  - The `player.id` comes from the `players` table lookup via `auth_id`, which is the verified JWT user ID.

### 2.3 BOT_PLAYER_ID Collision Risk

- **[PASS]** `BOT_PLAYER_ID = '00000000-0000-0000-0000-000000000000'` is the nil UUID. Supabase Auth uses UUIDv4 (random), which has a version nibble of `4` in position 13. The nil UUID has `0` in that position and can never be generated by UUIDv4. Collision is impossible.

### 2.4 SQL Injection

- **[PASS]** All database queries use the Supabase client's query builder (`.from().select().eq()` etc.), which parameterizes all values. No raw SQL strings are constructed.

### 2.5 CORS Headers

- **[WARN]** No CORS middleware is configured on the Express server. The iOS native app uses `URLSession` which does NOT enforce CORS (CORS is a browser-only restriction), so this works for the iOS client. However, if the admin dashboard (a web app) ever needs to call the practice endpoint, CORS will block it. **Not a blocker for the practice feature**, but should be addressed when the admin dashboard is built.
  - **Suggestion**: Add `cors` middleware to `index.ts` with an allowlist for the admin dashboard origin.

### 2.6 Reward Farming Prevention

- **[PASS]** Practice matches do not award energy or save records.
  - `finishPracticeMatch()` in `runner.ts` lines 314-316: explicitly comments "DO NOT save match record" and "DO NOT award chaos energy".
  - `finishMatch()` in `handler.ts` line 664: `if (state.mode !== 'PRACTICE')` gates the `saveMatchRecordAndAwardEnergy` call.
  - Both paths are covered (bot-initiated end and human-initiated surrender).

### 2.7 Rate Limiting

- **[WARN]** No rate limiting on `POST /api/practice/start`. A malicious client could spam practice match creation, creating many in-memory matches and Supabase Realtime channels without cleanup (if they never connect to play).
  - **Risk**: Memory exhaustion on the game server, Supabase channel quota exhaustion.
  - **Suggestion**: Add a simple in-memory rate limiter (e.g., max 3 concurrent practice matches per user, or max 1 practice match creation per 10 seconds per user). Could also add a match timeout that auto-cleans stale practice matches after 10 minutes of inactivity.

## 3. Logic Audit

### 3.1 Bot Deck Builder -- Empty Database Handling

- **[PASS]** `buildBotDeck()` in `ai.ts` line 72: checks `if (error || !templates || templates.length === 0)` and falls back to `generateFallbackDeck()` which creates 20 hardcoded vanilla creatures with a standard mana curve.

### 3.2 Bot AI -- Empty Hand

- **[PASS]** `decideBotMainPhase()` in `ai.ts` line 240: filters `bot.hand` through `.filter()` and `.sort()`. If the hand is empty, `playableCards` is an empty array, and the for loop produces zero actions. No crash.

### 3.3 Bot AI -- Empty Board (No Valid Attackers)

- **[PASS]** `decideBotAttackers()` in `ai.ts` line 292: iterates `bot.board` and skips `null` slots and dead creatures. If no valid attackers exist, returns an empty array. The runner (line 159) checks `if (attackerIds.length === 0)` and skips combat.

### 3.4 Bot Blocker Logic -- Taunt and Flying/Reach

- **[PASS]** `decideBotBlockers()` correctly handles:
  - Taunt creatures must block (first pass, lines 349-376).
  - Flying attackers can only be blocked by Flying/Reach creatures (lines 359-365, 390-397).
  - Each blocker/attacker pair is tracked via `usedBlockers` and `usedAttackers` sets to prevent double-assignment.

### 3.5 Bot Timing Delays

- **[PASS]** The `delay()` function in `runner.ts` line 322 uses `new Promise(resolve => setTimeout(resolve, ms))`. All bot actions use `await delay(...)` before acting, ensuring proper async timing. Constants: `BOT_THINK_DELAY_MS = 1500`, `BOT_ACTION_DELAY_MS = 800`, `BOT_BLOCK_DELAY_MS = 1000`.

### 3.6 Match Cleanup on Practice Match End

- **[PASS]** `finishPracticeMatch()` in `runner.ts` lines 296-319:
  - Calls `endMatch(state, endReason)` which removes match from in-memory store.
  - Calls `destroyTimerManager(matchId)`.
  - Calls `destroyRoom(matchId)` which unsubscribes the Supabase Realtime channel.
  - Does NOT save match record or award energy.

### 3.7 Human Can Surrender from Practice Match

- **[PASS]** `handleSurrenderAction()` in `handler.ts` line 458: `if (state.current_turn < 2 && state.mode !== 'PRACTICE')` allows early surrender when mode is PRACTICE.

### 3.8 Human Disconnect Cleanup

- **[WARN]** When the human disconnects from a practice match, the existing reconnection grace period and disconnect forfeit logic applies (via `TimerManager.onDisconnectForfeit`). However, the disconnect forfeit callback (handler.ts line 600-606) calls `forfeitMatch` then `finishMatch`, which will save a match record for non-practice matches. For practice matches, `finishMatch` correctly skips the record save. **This path works but has a subtle issue**: `forfeitMatch` calls `endMatch` which removes the match from memory, and then `finishMatch` calls `endMatch` again. The second `removeMatch` call is harmless (Map.delete on missing key), but `endMatch` also tries to compute `state.winner` which was already set. This double-call is pre-existing and not caused by the practice feature.

### 3.9 Stale Match Cleanup

- **[WARN]** If the human calls `POST /api/practice/start` but never connects to the Supabase Realtime channel, the match sits in memory forever. The 2-second `setTimeout` calls `startNextTurn`, which starts the turn timer. If the human never acts, the timer will eventually expire and track missed turns, but the practice match has no disconnect detection beyond the heartbeat mechanism. If the client never connects at all, heartbeats never start, and the match remains in memory indefinitely.
  - **Suggestion**: Add a "match start timeout" (e.g., 30 seconds after creation). If no player actions are received within that window, auto-cleanup the match.

## 6. CRITICAL Issues Found and Fixed

### CRITICAL-1: Double Bot Turn Execution

**Problem**: When a bot turn ends and the next turn starts, the bot turn was being scheduled TWICE:
1. `startNextTurn()` in `handler.ts` (line 635) checks `isPracticeMatch && shouldBotAct` and calls `executeBotTurn` -- **first invocation**.
2. `performBotEndOfTurn()` in `runner.ts` (lines 287-293) also checks `shouldBotAct` and calls `executeBotTurn` -- **second invocation**.

Both fire asynchronously and concurrently, causing the bot to play cards twice, declare attackers twice, corrupt game state, and likely crash the match.

The same pattern existed in the `setTimeout` in `index.ts` (lines 365-371): `startNextTurn` was called, and then the code also explicitly checked `shouldBotAct` and called `executeBotTurn`.

**Fix applied**:
- `runner.ts` `performBotEndOfTurn()`: Removed the redundant `shouldBotAct` check and `executeBotTurn` call after `startNextTurn`. Added a comment explaining why.
- `index.ts` setTimeout: Removed the redundant `shouldBotAct` check and `executeBotTurn` call after `startNextTurn`. Added a comment explaining why.

**Files modified**:
- `/Users/alexali/Projects/chaos-creatures/packages/game-server/src/bot/runner.ts` (lines 281-293)
- `/Users/alexali/Projects/chaos-creatures/packages/game-server/src/index.ts` (lines 358-373)

### CRITICAL-2: Surrender Does Not Destroy Room (Channel Leak)

**Problem**: `handleSurrenderAction()` in `handler.ts` called `forfeitMatch()` (which removes the match from memory) and `destroyTimerManager()`, but did NOT call `destroyRoom()`. This meant the Supabase Realtime channel subscription was never cleaned up on surrender. Over time, this would leak channel subscriptions, eventually hitting Supabase connection limits.

This affected BOTH PvP and practice matches, but was surfaced during the practice audit.

**Fix applied**: Replaced the body of `handleSurrenderAction` with a call to `finishMatch()`, which properly handles all cleanup: `endMatch` (removes from memory), `broadcastToRoom` (MATCH_END event), `destroyTimerManager`, `destroyRoom`, and conditional record save.

**File modified**:
- `/Users/alexali/Projects/chaos-creatures/packages/game-server/src/ws/handler.ts` (lines 452-465)

### CRITICAL-3: P1/P2 Swap Corrupts Hand Sizes and Chaos Spark

**Problem**: When `createMatch()` randomly assigns the human to PLAYER_2 and the bot to PLAYER_1, the practice endpoint swapped the player objects to force human=P1, bot=P2. However, the swap only reassigned `side` -- it did NOT fix hand sizes or Chaos Spark:
- P1 is dealt 4 cards (no Chaos Spark) by `createMatch`.
- P2 is dealt 5 cards (with Chaos Spark) by `createMatch`.
- After the naive swap, the human (now P1) had 5 cards + Chaos Spark, and the bot (now P2) had 4 cards + no Chaos Spark.
- This violates the game's fundamental turn economy: P1 goes first but has fewer cards; P2 goes second but gets an extra card and Chaos Spark as compensation.

**Fix applied**: After the swap, the code now:
1. Moves one card from P1's hand back to the top of P1's deck (reducing P1 from 5 to 4 cards).
2. Draws one card for P2 from P2's deck (increasing P2 from 4 to 5 cards).
3. Explicitly sets `has_chaos_spark = false` on P1 and `has_chaos_spark = true` on P2.

**File modified**:
- `/Users/alexali/Projects/chaos-creatures/packages/game-server/src/index.ts` (lines 326-348)
